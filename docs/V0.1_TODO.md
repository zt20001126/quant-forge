# Quant Framework V0.1 开发任务

> 本清单将 `docs/Personal_Quant_Framework_架构设计与长期演进指南.md` 拆为可逐步验收的迁移工作，并记录各 Phase 的实现状态。执行前先看根目录 `AGENTS.md`、`docs/architecture.md` 和本指南。旧 Demo 独立保留在 `E:\Quant\quant-learning`。

## V0.1 范围约束

CSV、单股票、日线、OHLCV、MA Cross、市价单、佣金与基础滑点、固定比例整股仓位计算、单持仓 Portfolio、回测结果、基础绩效和静态结果图、单元与集成测试。禁止把多资产、做空、杠杆、复杂风控、优化、事件总线、实盘、数据库或 Web 系统带入本版本。

## Phase 1：项目骨架

**目标**：建立可安装/运行/测试的 Python 项目骨架，同时保持旧 Demo 原位可运行。当前实现采用仓库根目录 `quant/` 包布局。

**创建/修改文件**：`pyproject.toml`、`quant/__init__.py`；按后续职责准备必要包目录；`tests/unit/`、`tests/integration/` 基础配置；可选更新 `.gitignore`。旧 Demo 保留在独立的 `quant-learning` 项目。

**核心接口**：尚不添加领域行为；明确包导入路径、最低 Python/运行依赖和测试命令。

**依赖**：无。

**测试要求**：验证新包可导入、测试工具可发现测试；旧 Demo 的运行命令仍成立（不要求本阶段改其行为）。

**Definition of Done**：新旧代码布局并存且边界写明；可重复安装开发依赖并运行空/骨架测试；README 或开发说明记录命令；没有大批无实现空模块。

**状态**：已完成。仓库根目录 `quant/`、基础 `pyproject.toml`、包导入测试、pytest 开发依赖、README 命令和 Python 构建产物忽略规则已建立。README/架构文档以此实际布局为准。

## Phase 2：Core Domain Model

**目标**：定义基础领域术语和值对象，令后续层通过稳定语义协作。

**创建/修改文件**：`quant/core/` 下实际需要的 `bar.py`、`enums.py`、`order.py`、`trade.py`、`position.py`，以及相应 `tests/unit/core/`。按必要性增减文件并同步架构文档。

**核心接口**：`Bar`、Side/订单类型、`OrderIntent`、`Order`、`Trade`、`Position`；明确数量单位、订单创建/执行时间、佣金字段及非法值规则。领域类型尽量不可变；状态型 Position 由 Portfolio 持有。

**依赖**：Phase 1。

**测试要求**：构造合法对象；拒绝无效时间、价格、数量、标的或费用；测试订单与成交关联及时间字段；验证 core 不导入具体基础设施。

**Definition of Done**：对象字段/不变量有文档和完整类型标注；命名一致；无需 pandas 即可使用；核心对象测试通过。

**状态**：已完成。领域对象及输入约束在 `quant/core/`；单元测试覆盖 Bar、目标仓位、订单/成交时间和持仓估值。

## Phase 3：Data

**目标**：把 CSV 适配与核心行情解耦，按时间顺序提供已校验 Bar。

**创建/修改文件**：`quant/data/base.py`、`models.py`（确有需要时）、`csv_feed.py`、`tests/unit/data/` 与 CSV fixtures。

**核心接口**：`DataFeed` 迭代/逐步产出 `Bar`；CSVDataFeed 接受路径和显式列映射/策略（如确有必要）。明确空文件、必需列、数值解析、日期排序、重复日期、OHLC 关系、正价格、非负成交量的处理规则。

**依赖**：Phase 2。

**测试要求**：有效 CSV、缺字段、空文件、坏日期/数值、NaN/Inf、非法 OHLC、重复日期和乱序输入；检查输出严格按时间递增。

**Definition of Done**：CSV 细节仅存在 Data 层；DataFeed 可被非 CSV 实现替换；每个输入边界有预期行为和测试。

**状态**：已完成。DataFeed Protocol 与 CSVDataFeed 已实现，乱序排序、重复日期、缺字段、非法 OHLC 和空输入有校验。

## Phase 4：Indicator

**目标**：提供可独立测试的简单移动平均计算，保持暖机期语义明确。

**创建/修改文件**：`quant/indicators/base.py`（仅有真实复用需求时）、`moving_average.py`、`tests/unit/indicators/`。

**核心接口**：对给定序列/Bar 历史计算 MA；定义窗口、暖机期未就绪状态和输入顺序。不要为单一 MA 强行建立复杂指标注册系统。

**依赖**：Phase 2；可并行于 Phase 3，但集成前接口须统一。

**测试要求**：手算样本、窗口边界、暖机期、窗口非法值、数据长度不足及输入无效值。

**Definition of Done**：指标没有文件读取、Broker 或 Portfolio 副作用；数值及 NaN/None 等未就绪语义有明确测试。

**状态**：已完成。滚动 SMA 使用 None 表示暖机期，含有效值及非法窗口测试。

## Phase 5：Strategy

**目标**：逐 Bar 决策并输出 OrderIntent；策略不操作账户或数据源。

**创建/修改文件**：`quant/strategy/base.py`、`ma_cross.py`、`tests/unit/strategy/`。

**核心接口**：Strategy 接收当前 Bar 和无未来信息的必要历史/指标上下文，返回意图列表；MA Cross 确定初始化状态、交叉判断、目标仓位/数量含义及重复信号规则。

**依赖**：Phase 2、Phase 4。

**测试要求**：暖机期、首次可交易状态、上下穿越、连续同向、重复调用、历史截断；验证信号时间为当前 Bar，意图不带未来执行价格，不导入 CSV/Broker/Portfolio。

**Definition of Done**：策略只产生意图；相同可见历史产生确定结果；接口不依赖 pandas 全表或资金内部状态；信号语义文档化。

**状态**：已完成。MA Cross 逐 Bar 使用历史收盘值，只产生空仓/满仓目标意图，不依赖数据源或账户。

## Phase 6：Broker

**目标**：依据订单与执行行情产生明确成交或拒绝结果，分离佣金和滑点规则。

**创建/修改文件**：`quant/broker/base.py`、`broker.py`、`commission.py`、`slippage.py`、`tests/unit/broker/`。

**核心接口**：Broker 执行可执行订单并返回 Trade/拒绝结果；最小 CommissionModel 与 SlippageModel；订单时间与执行 Bar 时间校验。资金可用性由 Portfolio/Engine 提供受控信息或由明确的执行授权流程处理，不得偷偷复制账户状态到 Broker。

**依赖**：Phase 2；订单生成依赖 Phase 5 的语义，但可先实现 Broker 单测。

**测试要求**：买卖成交价方向、手续费金额、无滑点/有滑点、无效价格数量、未来/过期订单、拒绝原因、交易成本边界。金额用容差或 Decimal 决策需记录。

**Definition of Done**：Broker 不产生策略判断、不拥有 Portfolio 状态；佣金/滑点可替换；每次订单均有成交或明确未成交结果。

**状态**：已完成。实现市价执行、百分比/固定佣金、无/固定/百分比滑点和可支付数量报价；Broker 不保存现金/持仓。

## Phase 7：Portfolio

**目标**：建立账户现金、单一标的持仓、成交入账和估值的唯一状态所有者。

**创建/修改文件**：`quant/portfolio/portfolio.py`（按需拆分 position manager）、`tests/unit/portfolio/`。

**核心接口**：`apply_trade(trade)`、`mark_to_market(prices/time)`、查询现金/持仓/组合价值；约束禁止负现金/负持仓，不允许未经成交直接改仓。

**依赖**：Phase 2；与 Phase 6 集成验证。

**测试要求**：初始资金、买入、部分/全部卖出、费用入账、资金不足/负持仓拒绝、重复成交保护（若有交易 ID）、市值与总资产恒等式、空仓估值。

**Definition of Done**：Portfolio 是账户状态唯一所有者；关键资金不变量有测试；Broker、Strategy、Engine 均通过公开接口协作。

**状态**：已完成。Portfolio 独占现金与持仓，校验重复成交、资金不足、超额卖出及费用，并按价格估值。

## Phase 8：Backtest Engine

**目标**：用清晰的时间语义编排 DataFeed、Strategy、Broker 和 Portfolio，产出完整结果。

**创建/修改文件**：`quant/engine/backtest_engine.py`、`quant/engine/models.py`（BacktestResult/Snapshot 若放此层）、`tests/unit/engine/`。

**核心接口**：Engine 构造时接收协作者；`run() -> BacktestResult`。固定生命周期：执行上根收盘信号的待处理订单于本根 Open → 入账 Trade → 按本根 Close 估值 → Strategy 观察完整本根 Bar 并产生后续订单。订单/信号/执行时间分别保留。

**依赖**：Phase 2、3、5、6、7。

**测试要求**：小型手算 OHLC fixture；证明 T 日 Close 信号只能在后续 Bar 执行（通常 T+1 Open）；滑点/佣金/估值时点正确；最后一根待执行意图有明确状态；末日持仓仍计入 Close Equity；无前视；重复运行行为明确。

**Definition of Done**：Engine 只编排；结果含交易、每日 Equity 和未执行订单状态；生命周期文档和测试一致；不存在同日 Close 信号同价成交。

**状态**：已完成。Engine 在执行 Bar 到达后才定量并以 Open 成交，记录 Signal/Execution Time、每日 Close Equity 和末日未执行意图；Engine 实例限制单次运行。

## Phase 9：Analytics

**目标**：对回测结果提供可解释且有边界定义的绩效指标。

**创建/修改文件**：`quant/analytics/metrics.py`、`report.py`（如需）、`tests/unit/analytics/`。

**核心接口**：基于 BacktestResult/Equity 序列计算 Total Return、Annualized Return、Max Drawdown、Sharpe；明确定义初始资本基准、空/短序列、无波动、年化交易日数、无风险利率和回撤符号。

**依赖**：Phase 2、8。

**测试要求**：逐项手算序列；首日资金基准、亏损/增长、平坦曲线、短序列、异常资产值、回撤及年化边界。

**Definition of Done**：Analytics 无交易副作用；每个公式/假设可追溯；实现指南要求的四项指标并有单元测试。

**状态**：已完成。实现初始资金基准的总收益、按 252 交易日年化收益、含初始资本峰值的最大回撤和日收益 Sharpe。

## Phase 10：Integration Test 与最终验收

**目标**：证明新框架可从 CSV 完整运行、维持分层约束，并与旧 Demo 做可解释的行为比较。

**创建/修改文件**：`tests/integration/test_backtest.py`、`tests/unit/test_visualization.py`、`quant/visualization/backtest_plot.py`、`examples/ma_cross_backtest.py`、`README.md`、`docs/architecture.md`、必要的项目配置。

**核心接口**：通过 composition root 组装 CSVDataFeed、MA Cross、Broker 模型、Portfolio、Engine 和 Analytics，输出可复现结果；可视化接收 Bar 序列和 BacktestResult，仅展示价格方向、实际成交位置和组合权益。

**依赖**：Phase 1–9。

**测试要求**：端到端从小型 CSV 到 Trade、Equity、指标；验证图表包含价格、买卖标记和权益曲线且不修改结果；运行完整测试套件和静态检查；检查旧 Demo 仍可运行；比较并解释因 T+1 Open、交易成本与新资金规则导致的结果差异。

**Definition of Done**：V0.1 指南 DoD 全部满足；Signal/Execution 区分；核心单元和集成测试通过；文档运行步骤准确；旧 Demo 未删除；风险/差异有记录；向用户提供具体测试命令和实际结果。

**状态**：已完成。CSV→DataFeed→MA Cross→Broker→Portfolio→Engine→Analytics 集成测试通过；真实 CSV 新框架示例可运行，旧 Demo 也通过非交互运行。两者在 `stock_real.csv` 上都是 31 笔交易，但期末资产分别为 139,307.19 与 146,176.65；同日 Close 与 T+1 Open 执行差异已记录在 `docs/architecture.md`。新增的结果图仅消费行情和结果，不影响成交流程。

## 推荐执行顺序

```text
Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Phase 6 → Phase 7
                                                     ↘ Phase 8 → Phase 9 → Phase 10
```

Phase 4 可以在 Phase 3 完成前独立实现；Phase 6 的纯成交模型也可先于 Portfolio 集成开发。Phase 8 必须等待 Strategy、Broker、Portfolio 的边界已固定。每阶段完成后先复核架构和测试，再进入下一阶段；核心接口或假设变化时先更新 `docs/architecture.md` 和本清单。
