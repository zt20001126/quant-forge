# Change Records

Change Record 用来保留重要开发任务的背景、原因、设计决策、实际修改范围、验证结果和影响，补充 Git Diff 难以表达的决策上下文。

## 何时创建

新功能、Bug 修复、核心逻辑修改、架构或模块职责调整、公共接口/数据模型变化、交易时间语义或交易成本规则变化、重要性能优化及重要工程化改造，应各建一份记录。

拼写修复、单纯格式化、注释措辞调整、小型 README 文字修正和无业务影响的简单清理通常不需要单独记录。避免为了凑记录而创建内容空泛的文件。

## 文件命名

```text
YYYY-MM-DD-序号-简短描述.md
```

日期使用变更发生日。同一天从 `001` 开始递增；创建前检查本目录中当天已存在的文件。描述使用简短、可搜索的英文 kebab-case，例如：

```text
2026-09-26-001-v0.1-engineering-review.md
```

## 编写要求

- 记录已完成的事实；涉及文件必须来自实际 Git Diff 或明确对应的已完成提交。
- 测试只写实际执行的命令和结果；未执行的项目写“未执行”并说明原因。
- 没有设计决策、影响或后续事项时，明确写“无”。
- 记录应解释修改原因，不能只罗列代码动作。

## 模板

复制以下模板创建新记录：

```markdown
# <变更标题>

## 基本信息

- 日期：YYYY-MM-DD
- 类型：Feature / Fix / Refactor / Docs / Test / Chore
- 影响范围：

## 变更背景

说明为什么需要这次修改。

## 变更内容

- 列出本次实际完成的修改。

## 涉及文件

- `path/to/actual-file.py`

## 设计决策

记录重要架构或业务决策；没有则写“无”。

## 测试与验证

- `实际执行的命令`：实际结果。
- 未执行项：写“未执行”及原因。

## 潜在影响

说明对 Strategy、Broker、Portfolio、Engine、Analytics、数据兼容性和 API 兼容性的影响；没有明显影响时明确说明。

## 后续事项

列出未完成事项；没有则写“无”。
```
